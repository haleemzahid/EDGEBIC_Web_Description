**To reopen a completed operation in EDGEBIC by User Solutions, clear its actual end date.** That single value is what separates frozen history from live work. With it removed, the operation returns to in progress, the next reschedule stops skipping it, and any hours still owed get planned forward onto the same work center.

Completing a step is covered in [how to complete an operation](/blog/how-to-complete-an-operation-in-edgebic). This is the reverse.

## Before You Start

| Prerequisite | Why |
|---|---|
| The job is not marked complete at the order level | A completed job locks actuals entry; use Reopen Job first |
| You know whether the hours are wrong too | Reopening clears only the end date, never the logged values |
| You intend to reschedule afterward | Reopening changes the classification; re-planning is a separate run |

## Step 1: Choose a Route

Three routes clear the same value. Pick whichever screen you are already on.

| Route | Where |
|---|---|
| Untick the mark-complete option and save | The **Log Actuals** dialog for the operation |
| Clear the **Actual End** cell | The **Job View** grid row, double-click to open the editor |
| Right-click the bar and clear the operation's actual end only | The **Schedule View** Gantt |

The Log Actuals route is the one to use when you are also correcting hours, because both changes land in the same save.

## Step 2: Clear the Actual End

Remove the value and save. The operation immediately shows as in progress: an actual start with no actual end.

If you also need to remove hours that were logged in error, zero every **Actual Hrs** and **Actual Pcs** cell in the grid and save without ticking mark-complete. Clearing hours does not clear the actual start, and clearing the actual start does not clear the end. Each of the three values is cleared on purpose, which is exactly why an accidental reopen costs nothing.

## Step 3: Reschedule

Reopening changes how the engine classifies the step. It does not by itself re-plan anything. Run a targeted reschedule for the job (the **Re-Schedule** button on the **Job View** tab, or on the **Schedule View** tab after saving changes) so the remaining hours get a real slot and the downstream steps queue behind the corrected picture. The safe way to run it is in [how to reschedule safely](/blog/how-to-reschedule-safely-in-edgebic).

## What Changes When You Save

| Surface | Effect |
|---|---|
| The operation's state | In progress: actual start present, actual end removed |
| Logged hours and pieces | Untouched, still on the days they happened |
| The Gantt bar | Drops the completed shade, shows the started state |
| Actual Live card | Status badge returns to Running |
| The audit trail | A reopen event is appended, carrying the actual end date that was removed |
| The next reschedule | The step keeps its work center, its logged hours stay locked, and only the remainder is re-planned |

That last row is the reason this matters. Before the reopen, a reschedule would have preserved the step as finished and never allocated the outstanding work at all. A job can be quietly under-planned by exactly the hours a mistaken completion hid.

## How to Check It Worked

Read the operation's row in the **Job View** grid: **Actual Start** carries a value, **Actual End** is empty. The **Actual Live** card shows **Running** rather than **Complete**, with its progress bar reading logged hours against planned. Then open **Job Audit** on the Job View tab. The newest event should be the reopen, showing the actual end date that was removed. Tracing those events is covered in [how to see who changed a schedule](/blog/how-to-see-who-changed-a-schedule-in-edgebic).

## Common Mistakes

- **Expecting the reopen to restore hours you already cleared.** It does not. Clearing the end and clearing the hours are independent actions, and reopening never puts values back.
- **Reopening but not rescheduling.** The classification is right and the plan is still wrong. Two moves, in order.
- **Clearing the actual start and leaving the end in place.** That produces a step that looks finished with no record of ever starting. Clear both or neither.
- **Reopening a step that is covered by its logged hours.** It will still read complete on screen. Fix the hours or the routing estimate instead.
- **Reopening when the real problem is a short confirm.** If the operator finished the physical work with fewer hours than planned, the step is genuinely complete and the site's partial-confirm policy decides what happens to the gap. See [how to record a partially finished operation](/blog/how-to-record-a-partially-finished-operation-in-edgebic).
