**An imported work center schedules only when it has three things: at least one instance, at least one shift, and an active flag. An import that mapped the name but skipped any of the three leaves the machine present but unable to offer a single working window.** [EDGEBIC by User Solutions](/edgebic) names exactly which one is missing through its pre-flight check and anomaly report, so the repair is targeted.

This post is part of the [EDGEBIC troubleshooting guide](/blog/edgebic-troubleshooting-guide). It covers the three requirements, how the tools tell them apart, and how to fix the import so it does not happen again.

## The Three Things a Machine Needs

A machine cannot produce capacity from a name alone. Scheduling requires all three of these, and an import that leaves any one blank produces a machine that looks configured but offers nothing.

| Requirement | What happens when it is missing |
|---|---|
| At least one instance | The engine has no physical slot to allocate, so capacity checks always fail |
| At least one shift | The engine finds no working windows and never places a job near term |
| Active flag on | The machine is treated as switched off and skipped entirely |

Imports commonly miss the instance count and the shift assignment, because those often live in a source column that was blank, unmapped, or stored differently in the old system.

## How the Tools Tell Them Apart

You do not have to guess which requirement is missing. EDGEBIC checks this in two places.

**Before scheduling, the pre-flight validator** checks that every machine on a routing has at least one instance and at least one shift. A machine with no instances fails pre-flight with a no-instances message. A machine with no shifts fails with a no-shifts message. Fixing pre-flight failures first means you do not burn a full scheduling run on a machine that was never going to place a job.

**After scheduling, the anomaly report's configuration-gap check** fires when a machine carries schedules but currently resolves no shift, whether because it never had them or because they were later removed. Its detail names the machine and confirms that neither the plant-wide shifts are on nor its own shift rows exist.

Read which one the tool names, because instances and shifts are separate causes with separate fixes.

## The Fixes

**No shifts.** Turn on the plant-wide shifts for the machine so it inherits the global working calendar, or add its own shift rows if it needs a different calendar than the plant. The [work center setup guide](/blog/how-to-set-up-work-centers-in-edgebic) covers both paths, and [giving one machine its own calendar](/blog/how-to-give-one-work-center-its-own-calendar-in-edgebic) covers the second.

**No instances.** Set the instance count to the number of physical units the machine represents. One machine is one instance; a bank of four identical units is four.

**Inactive.** Set the active flag on. An inactive machine is intentionally skipped, so this is only a fix if the machine should have been active.

After any of these, re-run scheduling. A machine that was pushing its jobs [far into the future](/blog/a-job-was-scheduled-far-in-the-future-edgebic) for lack of windows will start placing them near term.

## Fix the Import, Not Just the Machine

Repairing each imported machine by hand solves today's problem and guarantees tomorrow's. An [import mask](/blog/how-to-build-an-import-mask-in-edgebic) maps spreadsheet or database columns to work center fields, and the instance count, the plant-wide shifts flag, and the active flag can all be mapped from the source. Mapping them once means every future import arrives schedulable. EDGEBIC's [flexible import and export approach](/edgebic-erp-integration) is built around this: the mask is where you encode the mapping so imports are repeatable rather than one-off. The [troubleshooting guide](/blog/edgebic-troubleshooting-guide) links the neighboring capacity symptoms.
