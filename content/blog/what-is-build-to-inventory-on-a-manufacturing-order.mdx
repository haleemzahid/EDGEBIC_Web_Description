**Build-to-inventory on a manufacturing order is a per-order flag that decides whether one job builds to stock or to a specific demand, overriding the product's default make policy for that order alone. It has three states: unset means inherit the product's policy, true means build this order to stock, and false means treat this order as make-to-order.** It lets a single job deviate from the product's usual policy without changing the product's setting for every other order.

This entry is part of the [EDGEBIC by User Solutions](/edgebic) glossary series; for the wider vocabulary of planning, see the [manufacturing glossary](/blog/manufacturing-glossary). This flag is a per-order override of the [product's build method](/blog/what-is-a-build-method-in-manufacturing), the default policy it inherits from when left unset.

## How Build-to-Inventory Works

Every product carries a default make policy, its build method, that says how orders of that product are normally handled. Most orders should follow that default, and most of the time they do. But real shops occasionally need one job to behave differently, and changing the product's policy for a single exception is both heavy-handed and easy to forget to undo.

Build-to-inventory is the per-order escape hatch for exactly that situation. It is a three-state flag on the manufacturing order. Left unset, it means "inherit," and the order simply follows the product's build method as if the flag were not there. Set to true, the order builds to stock no matter the product default. Set to false, the order is treated as make-to-order no matter the product default.

The design keeps exceptions contained. Because the override lives on the order, not the product, flipping one job to build for stock has no effect on any other order of the same product. The product's default remains the source of truth for everything except the one job you deliberately singled out, and there is nothing to remember to reset afterward.

## A Concrete Example

Consider a shop that builds a custom bracket only when a customer orders it, so the bracket's build method is make-to-order. This week the shop has a quiet window on the press and wants to run one extra batch of brackets into finished-goods stock, ahead of an expected surge next month.

The wrong way to do this is to change the bracket's build method to make-to-stock, because that would change how every future bracket order is handled, and someone would have to remember to change it back. The right way is to create the extra manufacturing order and set its build-to-inventory flag to true. That single job now builds to stock, while every ordinary customer order of the bracket keeps following the make-to-order default untouched.

When the batch completes and moves into inventory, nothing needs unwinding. The exception was scoped to one order from the start, and the product's policy never moved.

## How EDGEBIC Uses It

Build-to-inventory is a manufacturing-order field that the planning engine reads to decide how a single job is treated.

- **Unset means inherit**, so the order follows the product's build method with no divergence.
- **True builds to stock** for that order alone, letting a normally make-to-order part be run into inventory as a one-off.
- **False forces make-to-order** for that order alone, letting a normally stocked part be tied to a specific demand.

An order also records what triggered it through its [demand source](/blog/what-is-a-demand-source-in-production-planning), which pairs naturally with how it is built. For the underlying policies this flag overrides, read [make-to-stock vs make-to-order](/blog/what-is-make-to-stock-vs-make-to-order).
