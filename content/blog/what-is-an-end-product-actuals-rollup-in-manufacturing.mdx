**An end-product actuals roll-up is a read-only summary that aggregates a job's operational actuals against the manufacturing order's single end product.** It reports actual start and end, hours, pieces, planned hours, percent complete, and an all-steps-done flag for the job's end item, and it deliberately excludes sub-assembly rollup rows and component splits so nothing double-counts. It is the canonical answer to the question every manager eventually asks: how far along is this job's end item?

This entry is part of the [EDGEBIC by User Solutions](/edgebic) glossary series; for the broader vocabulary of planning, see the [manufacturing glossary](/blog/manufacturing-glossary). For the per-step measure it aggregates, see [what is percent complete](/blog/what-is-percent-complete-in-manufacturing-scheduling).

## How an End-Product Actuals Roll-Up Works

A manufacturing order builds one end product, but the routing that makes it can be layered: sub-assemblies feed the end item, and some steps split into components. Actuals get logged all through that structure, step by step, as the floor does the work.

If you simply summed every actual on the job, you would double-count. A sub-assembly's hours already flow up into the end product's operations, and a component split represents the same physical work seen from a different angle. Adding the sub-assembly rollup rows and the component splits on top of the end-product operations would make the job look busier than it is.

The end-product actuals roll-up avoids that by aggregating only what belongs to the single end product, excluding the sub-assembly rollup rows and the component splits. What remains is a clean picture of the end item: when it actually started and ended, how many hours and pieces are logged, how many hours were planned, what percent is complete, and whether every step is done. Because it is a projection over the step-level actuals rather than a stored record, it always reflects the latest logged data.

## A Concrete Example

Job 42 builds one finished product through a routing that includes two sub-assemblies. As the floor logs actuals, hours accumulate on the sub-assembly steps and on the end product's own operations.

A manager asks how far along Job 42 is. Summing every row would over-count, because the sub-assembly hours are already reflected in the end product's operations. The end-product actuals roll-up instead reports on the end item alone: 62 percent complete, with 48 of 78 planned hours logged. That single figure is the honest progress of the finished product, not an inflated total.

When the last step finally closes, the roll-up's all-steps-done flag flips true. The manager no longer has to judge whether 98 percent means finished; the flag says it plainly. The roll-up gave a trustworthy running answer throughout and a definitive one at the end.

## How EDGEBIC Uses It

The end-product actuals roll-up is a read-only projection over a job's logged actuals:

- **It aggregates against the single end product**, reporting actual start and end, hours, pieces, planned hours, and percent complete for the job's end item.
- **It excludes sub-assembly rollup rows and component splits** so shared work is not counted twice, keeping the figures honest.
- **It carries an all-steps-done flag** that turns true only when every step is complete, giving a definitive finished signal beyond a high percentage.

The roll-up is the job-wide sibling of step-level [percent complete](/blog/what-is-percent-complete-in-manufacturing-scheduling): one summarizes a step, the other the whole end item. To feed it, log actuals on the steps with [how to log actual hours and pieces](/blog/how-to-log-actual-hours-and-pieces-in-edgebic), and read the roll-up for the clean end-item answer.
