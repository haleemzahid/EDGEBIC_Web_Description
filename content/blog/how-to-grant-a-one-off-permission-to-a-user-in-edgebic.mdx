**A per-user permission override in EDGEBIC by User Solutions grants or denies a single permission to one user, on top of whatever their roles provide, without altering the role itself.** It is the right tool for a genuine exception and the wrong tool for anything that describes a job. Here is how to set one, read it, and clear it.

Every task in this library is mapped on the [EDGEBIC how-to hub](/blog/edgebic-how-to-hub). For the role-based foundation this sits on, start with [how to create a role](/blog/how-to-create-a-role-in-edgebic).

## Before You Start

- The user already exists. Overrides attach to a user record.
- You have administrator rights on security.
- You have decided this is an exception rather than a job description. If more than two or three people need the same thing, it is a role.

## Step 1: Decide Override or Role

Run the question past two tests before you touch anything.

| Situation | Right tool |
|---|---|
| One person needs one extra thing, temporarily | Override |
| One person must be blocked from one thing their role allows | Override, used carefully |
| Several people share the same different need | A new role, assigned alongside |
| The need is permanent and describes their job | A role |

The reason to be strict about this is auditability. A role is self-documenting: its name says what it is for and anyone can read its permission set. An override is invisible unless you go looking at that specific user.

## Step 2: Open the User

Open **Settings**, then **Security**, then **Users**. Select the user and open the edit dialog.

## Step 3: Set the Override

In the **permission overrides** section, find the permission code and set it to granted or denied. Save.

Granting adds access the roles do not provide. Denying removes access the roles do provide. Both are recorded, and both take effect for that user only.

## Step 4: Understand the Combination Rule

The effective permission is straightforward once stated: role-granted or user-granted, minus anything user-denied.

That means a denial is the strongest signal in the system for that user. It will overrule a role that everyone in the plant assumes is authoritative, and because overrides do not appear in the role matrix, the role screen will happily keep showing the access as available.

Use denials sparingly, and write down why. A denial with no explanation is the access problem someone spends an afternoon on next quarter.

## Step 5: Clear an Override When It Is Done

In the same section, untick the override and save. The record is removed and effective access reverts to whatever the roles provide.

Two outcomes are possible, and both are correct.

- **Clearing a grant removes access**, if that override was the only thing providing it.
- **Clearing a denial restores access**, because the role was granting it all along.

Read the override before clearing it so you know which of the two you are about to cause.

## Step 6: Keep the List Short

Review overrides periodically. Temporary cover arrangements are the most common source, and they are also the ones nobody remembers to reverse. A user who covered a supervisor's imports for two weeks in March should not still be able to run imports in November.

If the same override keeps appearing on new users, that is the signal to build a role instead. Method in [how to create a role](/blog/how-to-create-a-role-in-edgebic).

## How to Check It Worked

- **Ask the user to try the action.** The direct test, and the only one that proves it.
- **Read the user's override list back.** Confirm exactly one row changed and it says what you intended.
- **Check a colleague on the same role is unaffected.** Overrides are per-user, so a second person on the same role should see no change at all. If they do, you edited the role by mistake.
- **Check the security audit log.** Permission changes are recorded there with the user and the timestamp. See [how to review the security audit log](/blog/how-to-review-the-security-audit-log-in-edgebic).

## Common Mistakes

- **Using overrides instead of roles.** Fifteen scattered overrides is an access model nobody can audit.
- **Forgetting overrides exist when diagnosing access.** The role matrix will not show them. Check the user.
- **Leaving temporary grants in place.** Set a reminder when you create one for cover.
- **Assuming a denial is redundant because the role does not grant it anyway.** Roles change. A denial left behind will bite the day someone updates the role legitimately.
