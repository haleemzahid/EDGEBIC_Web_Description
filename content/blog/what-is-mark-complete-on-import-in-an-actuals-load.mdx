**Mark Complete on Import is the actuals import option that marks each operation in the file as finished when its row lands, and it is overridden per row by the optional Complete column.** It answers a question a file of hours cannot otherwise answer: whether the work those hours represent is done, or merely done so far.

[EDGEBIC by User Solutions](/edgebic) offers it as a checkbox in the Import Options dialog for an actuals mask. This article defines what it changes and how it interacts with the per-row column. For where those hours land, see the sibling term [daily hour breakdown](/blog/what-is-a-daily-hour-breakdown).

## How It Works

An actuals row carries a job number, a work center, a date, and hours or pieces. That is enough to record what happened on a day, but not enough to say whether the operation is over. An operation that logged six hours on Tuesday might have finished on Tuesday or might still be running on Wednesday, and the two are treated very differently from that point on.

Mark Complete on Import supplies the missing statement as a blanket default: every operation the file touches is marked finished. The optional `Complete` column overrides it per row, so a row carrying an explicit value speaks for its own operation regardless of how the option is set.

What being complete means in practice is that the operation gets an actual end. Two consequences follow, and both are the reason the flag matters:

- **Rescheduling leaves it alone.** A completed operation is history. The engine preserves it exactly as recorded and plans only what remains.
- **Its hours count as done.** Progress rollups treat the operation as finished work rather than as work still outstanding.

An operation with logged hours and no end is in progress: its hours count, its remaining hours are still planned, and rescheduling may still move the part of it that has not happened.

## A Concrete Example

Think of a timesheet and a sign-off. The hours on the timesheet say what was worked. The sign-off at the bottom says the task is over. A batch of timesheets can be signed off as a batch, which is fast when they are all finished tasks, or signed individually when some of the work is still open. Signing the batch when part of it is still open is the mistake this option makes easy, and the per-row column is the remedy.

At Acme Industries a file covers three operations for **JOB-2026-0107**:

| Job | Work center | Date | Hours | Complete column | Result |
|---|---|---|---|---|---|
| JOB-2026-0107 | Saw-1 | 20 Jul | 4.0 | true | closed, end recorded |
| JOB-2026-0107 | CNC-Mill-1 | 21 Jul | 8.0 | true | closed, end recorded |
| JOB-2026-0107 | Weld-1 | 22 Jul | 3.5 | false | hours land, operation stays in progress |

With Mark Complete on Import ticked but the column present, the Weld-1 row still stays open, because the column wins. Had there been no column, all three would have closed and Weld-1's remaining hours would have vanished from the plan.

## How EDGEBIC Uses It

The option suits a specific shape of file: a batch that represents finished work, typically a period close or a backlog load where everything in the file is over. In that case ticking it once saves adding a column that would read true on every row.

For a recurring feed it is usually the wrong instrument, because a nightly or weekly export naturally mixes operations that closed with operations still running, and no single blanket setting is right for both. The per-row column is the better fit there, and it costs one column in the export.

Because actuals imports overwrite the days a file carries, correction is straightforward. Re-importing a corrected file replaces the earlier values for those days rather than adding to them, so a wrongly closed operation can be reopened by sending the same rows with the column set false. After reopening, run the scheduler so the remaining work is planned again; while the operation was marked complete the engine treated it as finished and stopped planning what was left.

The same completion state can be set from the Log Actuals screen and from the shop-floor kiosk, so an import is one of several routes to the same outcome rather than a separate mechanism.
