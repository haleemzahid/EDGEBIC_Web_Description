**Clearing an operation's actual start date in EDGEBIC by User Solutions returns it to not started, which is the only state in which the scheduler is free to move it again.** Somebody punched the wrong job, a terminal was bound to the wrong machine, or a start got recorded on the step below the one that ran. This is the correction, and the order to do it in.

For editing rather than removing a date, see [how to correct a wrong actual date](/blog/how-to-correct-a-wrong-actual-date-in-edgebic). Every task in this library is mapped on the [EDGEBIC how-to hub](/blog/edgebic-how-to-hub).

## Before You Start

- You are certain the start is wrong. Recorded work is protected everywhere else in the product, and this is one of the few places that protection is deliberately lifted.
- You know whether hours were also logged against the operation, because dates and daily hours are corrected separately.
- The job is not marked complete. A completed job locks actuals entry until you reopen it.

## Step 1: Find the Operation

Open the **Job View** tab and select the job. The grid lists one row per operation with its scheduled dates beside its actual dates, so the wrong row is usually obvious: it carries an actual start that the shop floor never made.

The Gantt tells the same story in color. An operation with only a start recorded shows the started state rather than the default one.

## Step 2: Clear the Actual Start

Clear the **Actual Start Date** cell so it is blank, and save. The operation reverts to not started.

Two things are worth knowing about this path:

- Clearing a start does not trigger the prior-operations prompt, because removing a start cannot create a gap upstream.
- Clearing a start does not clear an actual end. If an end is present, the operation is left claiming a finish with no beginning, which is an inconsistent state that reports badly everywhere.

## Step 3: Clear the End as Well, if There Is One

If the operation also carries an actual end, clear it too. Two routes do the same thing:

| Route | When to use it |
|---|---|
| Blank the **Actual End** cell on the Job View row | You are already in the grid correcting the start |
| Right-click the bar on the Gantt and clear both the actual start and end date and time for the operation | You are working visually and want both gone in one action |

If you only want to reopen a finished operation and keep its start, use the menu item that clears the actual end only. That is a different task, covered in [how to reopen a completed operation](/blog/how-to-reopen-a-completed-operation-in-edgebic).

## Step 4: Deal With the Hours

Dates and hours are separate records. If hours were logged on days that never happened, open the **Log Actuals** grid for the operation and correct or remove those day rows. When you change values that had been reported before, the dialog asks for a reason, which is stored in the logging history with the old value, the new value, and your name.

Give a real reason. "Fix" tells the next person nothing. "Punched onto wrong job, moved to JOB-2026-0104" tells them everything.

## Step 5: Reschedule

Press **Re-Schedule** to re-plan the affected job, or run the full schedule if the correction spanned several jobs. The un-started operation is now treated as not started, so the engine plans it from where the job really is, and it can place it on an alternate work center where the routing allows one.

## What Changes When You Clear

| Surface | Effect |
|---|---|
| The operation | Returns to not started once both actual dates are gone |
| The Gantt bar | Falls back from the started state and, after a reschedule, to the engine's planned position |
| Progress figures | Percent complete, remaining hours, and every report built on logged work recompute |
| The next reschedule | The operation is freely re-planned, including onto an alternate work center |
| Audit trail | The change is recorded, so the correction itself is inspectable |

## How to Check It Worked

Look at the Job View row: **Actual Start** and **Actual End** should both be empty, and the hours header should no longer count work the operation never did. Then run the reschedule and check the bar's state. A bar still showing a recorded state after a clear usually means one of the two dates survived, or a planned start pin is holding it.

## Common Mistakes

- **Clearing the start and leaving the end.** The operation then reports as finished with no beginning, and the health checks will flag the inconsistency.
- **Clearing the dates and leaving the hours.** Progress figures still count work against an operation that claims it never started.
- **Clearing instead of correcting.** If the work genuinely happened an hour earlier than recorded, edit the date rather than removing it.
- **Forgetting the other job.** A start recorded on the wrong operation usually means a real start is missing on the right one. Record it before you reschedule.
- **Expecting the plan to move on its own.** Clearing a date changes the record. The plan changes when the scheduler runs.
