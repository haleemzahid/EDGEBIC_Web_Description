**The security audit log in EDGEBIC by User Solutions records every access and account event: logins, failed logins, lockouts, logouts, user creation and deletion, activation and deactivation, password resets and changes, and permission grants and revocations.** It answers who got in, who could not, and who changed what about access. Here is how to open it and read it properly.

Every task in this library is mapped on the [EDGEBIC how-to hub](/blog/edgebic-how-to-hub). For the access model the log is recording, start with [how to create a role](/blog/how-to-create-a-role-in-edgebic).

## Before You Start

- You have the audit permission. Without it the screen does not appear, which is deliberate: an audit trail that everyone can read is a weaker control.
- You know the window you care about. "Recently" is not a filter, and the log grows with every login in the plant.
- You know whether the question is about access or about production. This log covers access only.

## Step 1: Open the Log

Open **Settings**, then **Security**, then **Audit Log**.

The grid arrives with one row per event carrying four fields.

| Field | What it gives you |
|---|---|
| **Event kind** | What happened, for example a failed login or a permission grant |
| **User** | Who the event concerns |
| **Context** | The specifics, which vary by event kind |
| **Timestamp** | When, and this is usually the field that resolves the question |

## Step 2: Filter Before You Read

Filter by date range or by username. Both narrow the grid to something a person can actually read.

Username first for an investigation about one person. Date range first when you are checking a window, for example the evening a change was noticed. The grid supports the standard filtering and grouping tools, covered in [how to filter a report with the filter editor](/blog/how-to-filter-a-report-with-the-filter-editor-in-edgebic).

## Step 3: Read the Event Kinds in Groups

The event kinds fall into three families, and thinking in families is faster than scanning the list.

1. **Session events.** Login succeeded, login failed, login locked out, logout. These answer who was in the system and when. A run of failures followed by a lockout is the classic sequence.
2. **Account events.** User created, user updated, user deleted, user activated, user deactivated, password reset, password changed. These answer what happened to an account.
3. **Access events.** Permission granted, permission revoked. These answer who changed what someone can do, and they are the rows to read first when access changed unexpectedly.

## Step 4: Read the Timestamps Together

A single row rarely settles anything. A sequence does.

- **Five failed logins in one minute, then a lockout.** A person mistyping, or a saved password on another device.
- **Failed logins spread across an hour, outside the person's shift.** Worth escalating.
- **A password reset, then failures, then a success.** Somebody was still using the old password somewhere.
- **A permission granted row followed by activity on a new screen.** The access change and its use, in order.

## Step 5: Go to the Right Log for Production Questions

If the question turns out to be about the plan rather than about access, this is the wrong log. Use [the reschedule history report](/blog/how-to-run-the-reschedule-history-report-in-edgebic) for schedule changes and [the job audit trail](/blog/how-to-run-the-job-audit-trail-in-edgebic) for what happened to one job.

Confusing the two costs time. "Who changed the schedule" is never answered here.

## How to Check It Worked

- **Your own login appears.** Filter to yourself and confirm today's session is recorded. If it is not, you are looking at a filtered view rather than an empty log.
- **A test event lands.** Change your own password, or grant and immediately clear a harmless override, then refresh and find the rows. This confirms recording is live rather than historical.
- **The timestamps match the clock.** Compare a known event against when you know it happened.

## Common Mistakes

- **Reading one row in isolation.** A failed login means almost nothing. Five in a row before a lockout means something.
- **Filtering by username on a partial spelling.** Exact matching on the wrong string returns an empty grid that looks like an absence of events.
- **Expecting production changes here.** Access only.
- **Only opening the log after an incident.** A short monthly read finds the account nobody deactivated when someone left, which is the thing most worth finding.
