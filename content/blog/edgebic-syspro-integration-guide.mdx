**Integrating SYSPRO with EDGEBIC means exporting the stock codes, work centers, bills of material, and open WIP jobs SYSPRO already holds to Excel, CSV, or a database view, mapping those columns once with a reusable import mask, and letting EDGEBIC schedule the work against finite capacity: real shift hours, real machine counts, and sequence-dependent setups.** Executable dates then go back as Excel. There is no e.net service to build against, no add-on to install inside SYSPRO, and no API sync to maintain when either side updates.

EDGEBIC by User Solutions is the newest generation of a scheduling line that has integrated with ERPs this way since 1991. Across 35+ years the same file-based approach has fed schedules for the US Navy, GE, BAE Systems, and Cummins. This guide covers the SYSPRO case: what to export, how the masks work, what the engine does with the result, and what a realistic first week looks like.

## Why a mid-market ERP still needs a finite capacity scheduler

SYSPRO handles the business well: orders, inventory, purchasing, financials, and the WIP and BOM records that hang off them. What most SYSPRO manufacturers report is that the daily sequencing decision still lands in a spreadsheet, because the questions a planner asks each morning are finite capacity questions:

- Which of these open WIP jobs actually fit on the two machining cells this week?
- If this rush job jumps the queue, whose promise date moves and by how much?
- Is the paint line loaded to 80 percent or 160 percent next Thursday?

Those require modeling shifts, machine instances, changeover sequences, and operator availability against every open job at once. It is a different computation from recording transactions, which is why a dedicated finite capacity layer beside the ERP is the standard pattern. The general case is in [finite versus infinite capacity scheduling](/blog/finite-vs-infinite-capacity-scheduling); the wider category view is on the [EDGEBIC ERP integration hub](/edgebic-erp-integration).

## The integration in one table

The [EDGEBIC ERP integration architecture](/edgebic-erp-integration) is identical for every ERP, SYSPRO included:

| Direction | Data | How it moves |
|---|---|---|
| SYSPRO to EDGEBIC | Stock codes | Excel or CSV export to Product import mask |
| SYSPRO to EDGEBIC | Work centers | Export to Workcenter import mask |
| SYSPRO to EDGEBIC | BOM / routing operations | Export to BOR (bill of routing) import mask, two-pass |
| SYSPRO to EDGEBIC | Open WIP jobs | Export to SalesOrder import mask |
| SYSPRO to EDGEBIC | Labor hours (optional) | Export to Actuals import mask |
| EDGEBIC to SYSPRO | Executable start and end dates, dispatch lists | Excel export from Job View and reports |

An **import mask** is a saved recipe. It remembers which kind of data you are importing, what format it arrives in (Excel workbook, or comma, semicolon, tab, or space delimited text), whether the first row is headings, whether text values are quoted, and how each column of your file maps onto an EDGEBIC field. You build it once by dragging your file's column headings onto EDGEBIC's target fields. Every run after that is two clicks.

Every row produces exactly one outcome: **Created**, **Updated**, **Reused** (matched and deliberately left alone), or **Failed** (rejected, with the reason recorded). A result dialog shows the counts and a per-run log file records every row individually.

## The file is the interface, and that is the advantage

A native service integration is a dependency: it has a version, a credential, and a failure mode that follows the vendor's release schedule rather than yours. A file or a database view has a much smaller failure surface. The only thing that can break is a column heading, and the fix is re-mapping one row in a mask.

Three practical consequences follow for a SYSPRO site:

- **Nothing is installed in SYSPRO.** No add-on, no e.net service you have to support through an upgrade, no schema change.
- **No integration credential exists.** The scheduler never authenticates against SYSPRO, so there is no permission surface to review or rotate.
- **Scheduling keeps working offline.** The plan is computed locally, so a database or network problem stops the export, not the shop's dispatch list.

## Step 1: the four exports

Four exports carry a complete scheduling model. SYSPRO produces these as report writer or query output to Excel or CSV; the exact column headings depend on your version and configuration, which is fine, because you map headings to fields once.

1. **Stock codes.** The stock code, description, unit of measure, and any cost or lead-time columns worth having visible. The code is the natural key, matched case-insensitively, so `BRK-200` in a file finds `brk-200` in the database.
2. **Work centers.** Identifier, how many identical machines the center really holds, default setup hours, efficiency, and an hourly rate for cost rollups. Bottleneck and shift-assignment flags ride in the same file.
3. **BOM and routing operations.** One row per operation: end product, work center, sequence number, hours per unit, setup time, queue time.
4. **Open WIP jobs.** Product, quantity, order reference, and dates.

Any SYSPRO list or report that saves to Excel or CSV is a valid source. A database view against the SYSPRO tables works equally well, since a mask can read a database source directly.

## Step 2: map the columns once

Build one mask per file and name it after the routine rather than the file: `Weekly SYSPRO WIP Jobs` outlives `jobs-week31.xlsx`. Mandatory fields are flagged, and the run refuses to start until they are mapped, so a half-built mask fails before it reads a single row.

Two mask features carry most of the weight:

**Unit conversion.** Set a conversion factor on any numeric column and the multiplication happens before the value is stored. Minutes to hours is `0.016667`, seconds to hours `0.000278`, and a standard time quoted per lot of 100 pieces becomes per piece with `0.01`. Different columns in the same file can carry different factors.

**Blank-cell preservation.** On an update run, a blank cell keeps the existing value rather than wiping it, so a partial refresh file is safe. Watch the matching rule: a zero is a value, not a blank. Leave a column out of the export rather than filling it with zeros you do not mean.

## Step 3: the routing import, and why it takes two passes

Routings are the hardest data to move between systems, because operations reference each other: step 10 feeds step 20 feeds step 30. A row-by-row import cannot wire those links, because step 20 does not exist yet when step 10 is written.

EDGEBIC's routing import runs in **two passes**. Pass one reads and validates every row, auto-creates any work center or product the file names that does not exist yet, and buffers the steps. Pass two groups the buffered rows by end product, sorts them by sequence number, writes them, and then wires the chain: 10 to 20, 20 to 30, and the terminal step to the finished product, so the routing renders as one connected flow in the [graphical routing designer](/blog/edgebic-graphical-bor-designer-tour).

Conventions that pay off immediately:

- **Number sequences in gaps of 10** so a later insert becomes 25 and nothing renumbers.
- **Keep all of one product's steps in one file.** A routing import wipes and recreates that product's steps once per run, which is what makes re-imports idempotent; splitting one product across two runs means the second run's wipe deletes the first.
- **Re-importing is safe for running jobs.** Every scheduled job carries a frozen snapshot of the routing it was planned with, so a routing change applies to future jobs and leaves work in progress untouched.

## Step 4: WIP jobs in, then run the scheduler

The order import maps product, quantity, reference, and dates. When your export carries a sales order reference, rows sharing that reference group under one order and their jobs auto-number as `{Ref}-{line}`, keeping a multi-line order together while still carrying your original SYSPRO job number.

**Imports never schedule anything.** Imported jobs sit as unscheduled demand until you run the scheduler, which states its scope in plain numbers before it plans. Data movement and planning stay separate on purpose. The choices are covered in [EDGEBIC scheduling modes explained](/blog/edgebic-scheduling-modes-explained).

Once the data is in, the full engine applies: finite capacity across multiple shifts and machine instances, [work center groups](/blog/edgebic-work-center-groups-explained) that re-shop the machine pool on every reschedule, a [sequence-dependent setup matrix](/blog/edgebic-setup-matrix-explained), lot streaming with transfer batches, operator skills, and mathematical optimization with a proven optimality gap. The [EDGEBIC product overview](/edgebic) maps the engine.

## Step 5: sending dates back

The return trip is Excel. The Job View grid exports the job schedule as a workbook with colored cells and a legend sheet, the work center schedule exports the same way, and every report dialog exports to Excel or PDF using the column layout you saved. Revised dates then go back into SYSPRO through the WIP job date-maintenance path your process already uses. There is no automated write-back, which keeps your ERP data under your team's control.

The method has a documented benchmark in the User Solutions lineage: at Plastilite Corporation the ERP vendor itself recommended User Solutions scheduling, and the team went from first export to a complete optimized schedule with ERP integration in 5 days. A mid-size SYSPRO manufacturer usually follows the same shape.

| Day | Work |
|---|---|

| 2 | Export BOMs and operations; build the routing mask with unit conversions; review the routing designer |
