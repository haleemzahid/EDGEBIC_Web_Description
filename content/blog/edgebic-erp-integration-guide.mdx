**EDGEBIC ERP integration** means one thing, consistently: your ERP produces a file or a read-only query, EDGEBIC reads it through a saved import mask, and the finite capacity schedule that comes out goes back to your team as a plan the floor can follow. There is no native connector, no certified plugin, and nothing installed inside your ERP. EDGEBIC by User Solutions connects to every ERP the same way, which is precisely why the method survives an ERP version upgrade, a second plant, or a switch to a different ERP entirely.

This guide is the map of that subject. It covers what the import masks actually cover, the three ways data can reach EDGEBIC, how to map your ERP's fields, what you can never import and must therefore plan for, and the weekly rhythm that keeps a schedule current without turning into a project.

## The Architecture, Stated Plainly

User Solutions has been building scheduling tools for manufacturers since 1991, across the RMDB lineage and now EDGEBIC. The integration approach has not changed because it has not needed to: [EDGEBIC connects to every ERP the same way](/blog/why-edgebic-connects-to-every-erp-the-same-way), through files and queries rather than through a connector that has to be written, certified, and maintained per system.

Three consequences fall out of that, and they are worth stating before you plan anything:

1. **Nothing is installed in your ERP.** Your ERP team is asked for a report or a read-only view, not for a development project. [Specifying the export you need from IT](/blog/specifying-the-erp-export-you-need-from-it) is usually a single conversation.
2. **An ERP upgrade does not break the integration.** If the export still produces the same columns, nothing changes. If the column order shifts, [handling an export that changed column order](/blog/handling-an-erp-export-that-changed-column-order) is a mask edit, not a rebuild. There is a short list of [things to check after an ERP version upgrade](/blog/what-to-check-after-an-erp-version-upgrade).
3. **Replacing the ERP does not mean replacing the schedule.** [What changes in EDGEBIC when you replace your ERP](/blog/what-changes-when-you-replace-the-erp-behind-edgebic) is mostly the masks. The routings, work centers, and history stay put.

## The Eight Import Masks

This is the single most important fact in this guide, and the one most integration plans get wrong. The import masks cover **exactly eight entity types**: Product, Workcenter, Customer, SalesOrder, BOR, Actuals, PlantHoliday, and Shift.

An [import mask](/blog/what-is-an-import-mask) is a saved recipe. It remembers the entity type, the file format, whether the first row is headings, and how each column in your file maps to a field in EDGEBIC. You build it once, and every run after that is two clicks. Every row lands as Created, Updated, Reused, or Failed, and the [per-run import log](/blog/what-is-an-import-run-log) records each outcome.

Start by working out [which ERP fields EDGEBIC needs to build a finite capacity schedule](/blog/which-erp-fields-edgebic-needs-to-schedule), then decide [how many import masks your shop actually needs](/blog/how-many-import-masks-your-shop-actually-needs). Most shops need four, not eight.

Everything outside those eight is hand-entered: departments, work center groups and their members, operators with their skills and certifications and rosters, the sequence-dependent setup matrix, quotes, and scenarios. That is a real cost and you should budget it rather than discover it, which is what [what EDGEBIC cannot import, and how to handle it](/blog/what-edgebic-cannot-import-and-how-to-handle-it) exists to cover.

Two behaviors deserve emphasis because they surprise people:

- **A BOR re-import replaces that product's entire routing per run.** All of one product's steps must be in one file. That is safe by design, and it is also how [engineering changes travel through a routing re-import](/blog/handling-engineering-changes-via-erp-re-import).
- **Imports never schedule.** Loading data and building a plan are separate actions. A nightly refresh cannot quietly rewrite a plan the floor is working to.

## Three Ways Data Gets In

**Manual file import.** Export from the ERP, open Import in Settings, run the saved mask. This is where every integration starts and where many stay.

**A watched file.** The Integration tab turns an existing mask into a repeating sync. Your ERP drops a file on a share, EDGEBIC notices, waits for the file to stop changing, and runs the mask. See [scheduling a nightly ERP export and import routine](/blog/scheduling-a-nightly-erp-export-import-routine), and then [reading the import log after a nightly run](/blog/reading-the-import-log-after-a-nightly-erp-run), which is the discipline that keeps automation honest.

**A read-only external SQL query.** The same Integration tab can read a result set directly from an external SQL Server on an interval. [Connecting EDGEBIC to your ERP database with a SQL source](/blog/connecting-edgebic-to-your-erp-database-with-a-sql-source) walks it through. The mask is unchanged: a query's columns are treated exactly like a file's headings.

Choosing between them is a real decision with real tradeoffs, covered in [CSV vs database view](/blog/csv-vs-database-view-erp-export-tradeoffs). A related decision is [how often each data type should be imported](/blog/deciding-erp-import-frequency-by-data-type), because routings and orders do not need the same cadence.

## Mapping Your ERP's Fields

The mapping work is where integrations succeed or stall, and almost all of the difficulty is in routings. The recurring problems are well documented:

- [Mapping routings vs operations from your ERP](/blog/mapping-routings-vs-operations-from-your-erp), which is the shape question you answer first
- [Importing your ERP's operation sequence numbers](/blog/importing-erp-operation-sequence-numbers)
- [Handling an export with combined setup and run time](/blog/handling-combined-setup-and-run-time-from-your-erp)
- [When your ERP exports setup as its own operation row](/blog/when-your-erp-exports-setup-as-its-own-operation-row)
- [Mapping your ERP's units of measure for scheduling](/blog/mapping-your-erps-units-of-measure-for-scheduling), where a conversion factor turns minutes into hours during the import
- [Splitting one ERP operation into multiple EDGEBIC steps](/blog/splitting-one-erp-operation-into-edgebic-steps)
- [Mapping alternate work centers from your ERP](/blog/mapping-alternate-work-centers-from-your-erp)
- [Importing sub-assembly routings](/blog/importing-subassembly-routings-from-your-erp)

On the resource side, [when two ERP rows map to one EDGEBIC work center](/blog/when-two-erp-rows-map-to-one-edgebic-work-center) is common in shops whose ERP models a cell as several cost centers, and [building a work center list when your ERP has none](/blog/building-a-work-center-list-when-your-erp-has-none) covers the case where the ERP simply has no resource model.

On the demand side, decide early [which work orders to import](/blog/deciding-which-erp-work-orders-to-import), how to treat [customer due dates versus internal need dates](/blog/importing-customer-due-dates-vs-internal-need-dates), and how [ERP order priority maps into your schedule](/blog/mapping-erp-order-priority-into-your-schedule). Keep [job numbers aligned between the two systems](/blog/keeping-job-numbers-aligned-between-erp-and-edgebic) from day one, because retrofitting that is painful.

Two questions that look technical but are actually governance: [choosing the system of record for each scheduling field](/blog/choosing-the-system-of-record-for-each-scheduling-field), and [whether to trust your ERP's standard times](/blog/should-you-trust-your-erps-standard-times). Neither has a universal answer, and getting them wrong produces a schedule nobody believes.

Calendars are the one place plans routinely go wrong in the other direction. PlantHoliday and Shift are two of the eight masks, so [importing your ERP's manufacturing calendar](/blog/importing-shift-calendars-and-plant-holidays-from-your-erp) is available, and hand-entry is a legitimate choice when you have only a few shift patterns rather than a requirement.

## Going Live, Then Staying Live

Getting started is bounded work. Follow [the first-week ERP integration checklist](/blog/a-first-week-erp-integration-checklist), then [the go-live cutover plan](/blog/an-erp-and-edgebic-go-live-cutover-plan). Before the first live run, [test any mask change before the live run](/blog/testing-an-import-mask-change-before-the-live-run), and afterwards work [the import reconciliation checklist](/blog/an-erp-import-reconciliation-checklist) so counts are verified rather than assumed.

Steady state is a rhythm, not a project. [The weekly import routine](/blog/keeping-erp-and-edgebic-in-sync-weekly-import-routine) is the baseline, [keeping product masters in sync](/blog/keeping-product-masters-in-sync-erp-edgebic) is the recurring maintenance, and [a monthly ERP to EDGEBIC data audit](/blog/a-monthly-erp-to-edgebic-data-audit) catches the drift a weekly run does not. Assign it: [who owns the import routine on your team](/blog/who-owns-the-erp-import-routine-on-your-team) is a governance question with a real answer, and [keeping a change log of mask edits](/blog/keeping-a-change-log-of-import-mask-edits) is what makes an integration survive a personnel change.

Actuals flow the other way. [Importing ERP labor transactions as scheduling actuals](/blog/importing-erp-labor-transactions-as-actuals) is the alternative to kiosk entry, with a known edge case in [when your ERP labor file starts mid-routing](/blog/when-your-erp-labor-file-starts-mid-routing). Then [reconciling work order quantities after partial completion](/blog/reconciling-erp-work-order-quantities-after-partial-completion) and [closing ERP work orders that EDGEBIC still thinks are open](/blog/closing-erp-work-orders-that-edgebic-still-thinks-are-open) close the loop.

Sending the plan back out is a grid export, not a round-trip module: [exporting the EDGEBIC schedule back to your ERP](/blog/exporting-the-edgebic-schedule-back-to-your-erp) explains what that means in practice. A [grid export snapshot](/blog/what-is-a-grid-export-snapshot) is for sharing and analysis and is deliberately not an import file.

## The Harder Cases

Some shops do not fit the standard shape. [Scheduling when your ERP has no routing data](/blog/scheduling-when-your-erp-has-no-routing-data) is more common than vendors admit. [Handling multi-plant exports](/blog/handling-multi-plant-erp-exports-in-edgebic) and [onboarding a second plant into the same database](/blog/onboarding-a-second-plant-into-the-same-edgebic-database) cover growth. [Scheduling a shop that runs two ERPs](/blog/scheduling-a-shop-that-runs-two-erps) covers the aftermath of an acquisition. [Running EDGEBIC alongside your ERP's scheduling module](/blog/running-edgebic-alongside-your-erps-scheduling-module) covers the political reality of not switching everything at once.

When something goes wrong, most of it is mundane: [what to do when the ERP export is late or missing](/blog/what-to-do-when-the-erp-export-is-late-or-missing), and [handling part number revisions on import](/blog/handling-erp-part-number-revisions-on-import). Two decisions sit outside the software entirely: [who should see your ERP export files](/blog/who-should-see-your-erp-export-files), and [what an ERP integration costs in hours per week](/blog/what-an-erp-integration-costs-in-hours-per-week), which is the number to quote when someone asks.

Finally, the honest limit: [what your ERP export cannot tell you about the floor](/blog/what-your-erp-export-cannot-tell-you-about-the-floor). A file carries the data the ERP holds, and the ERP does not hold the reason a machine sat idle on Tuesday. That gap is closed by logging actuals, which the [shop floor guide](/blog/edgebic-shop-floor-guide) covers, not by a better mask.
